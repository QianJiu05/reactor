# 账号体系设计文档

> 目标：把「采集端」与「查看端」通过**账号**天然绑定，替代当前
> 「相机注册时指定查看端 fd」和「广播给所有查看端」的做法。
>
> 本文只做设计，不含实现。

---

## 〇、本版决定

| 项 | 决定 |
| --- | --- |
| 账号来源 | **服务器预分配**（`accounts.conf` 一行一个账号） |
| 绑定关系 | **一账号 ⇄ 一采集端 + 多查看端** |
| 认证方式 | **只用账号名登录，不校验密码** |
| 密码字段 | `struct account` 中**保留 `password[64]` 字段但不使用**，留作后续扩展 |
| 采集端握手 | `CAM <account>\r\n`，**服务器回一行** `OK` / `ERR AUTH` / `ERR BUSY` |
| 查看端标识 | **账号写在 URL 路径第一段**，如 `GET /alice` |
| 路径层级 | **只支持一层**：`/alice` 有效，`/alice/xxx` 一律 404 |
| `GET /` | 回 `503` + 提示页，**不列出可用账号**（`ALLOW_INDEX_PAGE` 默认 0） |
| 并发同步 | 账号表用单把全局互斥锁；帧转发路径不持锁 |

**相比引入密码校验的版本，本版省掉了**：SHA-256 实现、`WWW-Authenticate` / 401 流程、
Base64 解析、浏览器认证弹框交互。实现规模从约 900 行降到约 600 行。

## 一、设计目标与边界

### 1.1 目标

| 编号 | 目标 |
| --- | --- |
| G1 | 采集端用**预分配的账号**注册，服务器校验账号合法性后才接受视频流 |
| G2 | 查看端用**同一账号**访问，只看到该账号绑定那一路视频 |
| G3 | 账号之间完全隔离，互不可见；非法账号一律拒绝 |
| G4 | 采集端不在线时，查看端能得到明确反馈而不是静默挂起 |
| G5 | 采集端断线重连无需人工干预；查看端不因此掉线 |

### 1.2 明确的非目标

- **不做**密码校验、在线注册、找回密码、权限分级
- **不做**一账号多设备（一账号 = 一路通道）
- **不做**TLS/HTTPS（受课题范围限制，在 §8 记录为已知风险）

> **安全边界必须写清楚**：本版**只靠账号名区分通道，不构成任何身份认证**。
> 任何人只要知道账号名就能看该通道的视频，也能尝试用该账号名注册采集端
> （会被"已有采集端"规则挡住，见 §7.3）。
> 论文里应明确表述为"**账号作为通道标识与访问凭据的占位设计，密码校验留作扩展**"，
> 而不是描述成"实现了访问控制"。

## 二、现状与差距

### 2.1 当前连接识别流程

```
                         recv_callback()  [src/recv.c:28]
                                │
                        recv() 收到字节，追加到 conn->inbuf
                                │
                 serve_type == NOT_INIT || == HTTP ?   [recv.c:56]
                                │ 是
                    parse_serve_type(conn)  [recv.c:18]
                                │
        ┌───────────────────────┼───────────────────────┐
        │ "GET "                │ "CAM"                 │ 其它
        ▼                       ▼                       ▼
   SERVE_HTTP            SERVE_GET_RESOURCE        SERVE_ECHO
        │                       │                       │
 generate_http_response()  handle_resource()      echo_callback
        │                       │
 send_cb = http_callback   send_cb = http_callback
```

### 2.2 差距清单

| 编号 | 现状 | 影响 |
| --- | --- | --- |
| D1 | `parse_serve_type()` 只看首行前 4 字节，不提取任何标识 | 无通道概念，无法绑定 |
| D2 | `viewer_broadcast()` 遍历全局 `g_viewers[]` | 所有查看端收到所有相机的帧，零隔离 |
| D3 | `struct_http.path` 已定义但**全项目无一处赋值**（[struct_http.h:12](codes/reactor/inc/http/struct_http.h#L12)） | 无法按路径路由，`GET /alice` 和 `GET /favicon.ico` 被同等对待 |
| D4 | 无任何账号校验逻辑 | 任何人连上就能看 |
| D5 | 账号状态若按直观写法放进全局变量 | **多 reactor 线程并发访问 → 数据竞争**（见 §6.1） |
| D6 | 握手行解析依赖「首包不少于 4 字节」 | TCP 分片时误判（见 §5.2） |
| D7 | 握手后 `memset(conn->inbuf, 0, CONNECT_BUF_LEN)` 清空整个缓冲 | 同一包里的首帧被丢弃（见 §5.3） |
| D8 | `sub_init` 信号量在 `epoll_create` **之前**发出（[reactor.c:37](codes/reactor/src/reactor.c#L37) vs [reactor.c:71](codes/reactor/src/reactor.c#L71)） | 跨线程 `set_epoll()` 可能在 epfd 未创建时失败，且返回值被忽略（见 §6.4） |

## 三、账号模型

### 3.1 核心约定

```
        账号 (account)
             │
      ┌──────┴──────┐
      │             │
  采集端          查看端
 （0 或 1 个）   （0 ~ N 个）
```

- **一个账号最多绑定一路采集端**。第二个用同账号注册的采集端被**拒绝**（不顶替，见 §7.3）
- **一个账号可被多个查看端同时订阅**（多浏览器 / 多终端）
- 账号生命周期与采集端连接**解耦**：采集端不在线时账号依然存在，查看端可正常访问并等待

### 3.2 账号表数据结构

```c
#define MAX_ACCOUNTS      64    /* 账号总数上限 */
#define MAX_VIEWERS_PER   32    /* 单账号查看端上限 */
#define ACCOUNT_NAME_LEN  32

struct account {
    char     name[ACCOUNT_NAME_LEN];      /* 账号名，即 URL 路径第一段 */
    char     password[64];                /* 预留：本期不校验，留作后续扩展 */
    int      used;

    int      cam_fd;                      /* 绑定的采集端 fd，-1 = 未绑定 */
    int      viewers[MAX_VIEWERS_PER];    /* 该账号的查看端 fd，-1 = 空槽 */
    int      viewer_count;

    /* 运行统计，便于演示与论文写作 */
    unsigned long frames_in;              /* 累计收到的帧数 */
    unsigned long frames_out;             /* 累计转发帧数 */
    int64_t  last_frame_ms;               /* 最近一帧时刻，用于僵死判定（§7.3） */
    int64_t  cam_online_since;            /* 采集端上线时刻，0 = 离线 */
};

static struct account g_accounts[MAX_ACCOUNTS];
```

> `password` 字段保留但不读取。配置文件里也保留该列（留空），
> 这样后续启用校验时**不需要改数据结构，也不需要迁移配置文件**。

### 3.3 反向索引：fd → 账号

**它不是为断线重连设计的**，而是为了**连接关闭时快速定位它属于哪个账号**。

`close_callback()` 收到的是一个 `struct connect*`，它只知道自己的 fd，
需要回答两个问题：

```
一个连接 fd=12 断了
   ↓
它是采集端还是查看端？
   ↓
是采集端 → 要找到它绑的是哪个账号，把该账号的 cam_fd 置回 -1
是查看端 → 要找到它订的是哪个账号，从该账号的 viewers[] 里摘掉 fd=12
```

"找到它绑的是哪个账号"这一步，**没有反向索引就只能遍历 64 个账号去找 `cam_fd == 12`**。
反向索引把 O(账号数) 的扫描变成 O(1) 取值：

```c
/* fd 直接做下标。服务器不对已建立的连接做 dup，fd 在连接存续期内唯一，
 * 且直到 close_callback() 才释放，所以这个映射是安全的。 */
#define ACCOUNT_OF_CAM_MAX   (NUM_OF_CONNECTOR * 8)
static int g_account_of_cam[ACCOUNT_OF_CAM_MAX];   /* 值 = 账号下标，-1 = 无 */
```

#### 与断线重连的关系（澄清）

重连**不依赖**反向索引，依赖的是账号里的 `cam_fd` 被置回 `-1`：

```
① 采集端掉线 → close_callback → account_unbind_camera(12)
                                  → g_accounts[3].cam_fd      = -1   ← 账号被"腾空"
                                  → g_account_of_cam[12]      = -1   ← 索引清掉
② 采集端重连（新 fd=15）→ CAM alice → account_verify("alice") → 下标 3
                                    → account_bind_camera(3, 15)
                                    → g_accounts[3].cam_fd      = 15
                                    → g_account_of_cam[15]      = 3   ← 重新登记
```

#### 复杂度对照

| | 作用 | 不用它会怎样 |
| --- | --- | --- |
| `g_accounts[i].cam_fd` | **账号 → 采集端**，查看端访问时用它找视频源 | 找不到视频源，功能不成立 |
| `g_account_of_cam[fd]` | **采集端 fd → 账号**，断线时用它定位要清哪个账号 | **功能仍正确**，但要遍历账号表，O(n) |

> **第一版可以先不做**，直接写 `for (i = 0; i < MAX_ACCOUNTS; i++) if (g_accounts[i].cam_fd == fd) ...`。
> 账号数 ≤ 64 时性能无差别。文档推荐它，是因为它只值 10 行代码，
> 却能让断线处理的语义变清晰、也便于论文里讲"索引设计"。

## 四、账号配置

### 4.1 配置文件

路径由 `config.h` 的 `ACCOUNT_FILE` 指定，默认 `./accounts.conf`。

```
# 一行一个账号。格式：account[:password]
# 密码列本期留空、不校验，保留是为了后续启用时无需改格式。
alice:
bob:
```

解析规则：

- 跳过空行和 `#` 开头的注释行
- 按 `:` 切成两段；只有一段也可以（视为无密码）
- 账号名非法（见 §4.2）的行**跳过并打印行号**，不中断启动
- 账号名重复的行，保留第一个，后续的跳过并告警

### 4.2 账号名合法性约束

```
合法：^[A-Za-z0-9_]{1,31}$
```

**两个必须拒绝的情况**：

1. **含 `/` 或 `?` 或 `#` 或空格** —— 会破坏 URL 路径解析
2. **等于保留字 `favicon.ico`** —— 见 §5.5，它和浏览器的自动请求冲突

> 这组约束必须在**三个地方**一致校验：配置加载时、采集端握手时、查看端路径解析时。
> 建议只写一个 `account_name_valid()` 函数，三处都调它。

### 4.3 配置文件缺失时

启动时告警，**服务器仍然监听端口**，但：

- 任何采集端握手都返回 `ERR AUTH`（账号表为空）
- 任何查看端路径都返回 `404`

这样便于先起服务再修配置，不用反复重启。

## 五、协议设计

### 5.1 采集端握手与服务器回应

**现状**：`CAM\r\n`（无账号）

**改为**：

```
CAM <account>\r\n
```

例：`CAM alice\r\n`

**服务器回应**（已确认要加）：

| 情况 | 回应 | 后续动作 |
| --- | --- | --- |
| 账号存在且未被占用 | `OK\r\n` | 保持连接，开始进入帧解析状态 |
| 账号不在配置表里 / 账号名非法 | `ERR AUTH\r\n` | 发送后关闭连接 |
| 该账号已有采集端在线且未僵死 | `ERR BUSY\r\n` | 发送后关闭连接 |

**采样端需要同步改造**（`codes/webcam/src/video_sender.c`）：

现在 `connect_with_retry()` 发完握手就立刻进推流循环，要改成：

```
① connect()
② 发送 "CAM <account>\r\n"
③ 按行读取回应（同样要按完整行判定，见 §5.2）
     "OK"       → 进入推流循环
     "ERR AUTH" → 打印"账号不存在"并退出（或定时重试）
     "ERR BUSY" → 打印"该账号已有设备在线"并退出（或定时重试）
④ 同时注意回应之后可能紧跟服务器发来的其它字节，要保留（见 §5.3）
```

> **边界情况**：回应和第一帧无关（第一帧是采集端发给服务器的），
> 但服务器在 `OK\r\n` 之后可能因为别的原因断连，采集端要能处理。

### 5.2 握手行必须按「收到完整一行」解析（修 D6）

**现状问题**：`parse_serve_type()` 在首包 ≥ 4 字节时就下判断。
如果 TCP 把 `CAM alice\r\n` 分片成先到 `CAM `、后到 `alice\r\n`，
第一次解析时 `conn->inbuf` 里没有 `\r\n`，判定就会出错。

**正确做法**：引入"尚未收到完整首行"的阶段，只有在 buffer 里**找到 `\r\n`** 时才解析：

```
每次 recv 之后（仅 PHASE_PRE_AUTH 阶段）：
    在 inbuf 中查找 "\r\n"
    未找到 → 若 inlen > MAX_HANDSHAKE_LEN(128) 判定非法，回 400 或直接关闭
             否则 return，等待下一包
    找到了 → line_len = 位置 + 2
             解析首行 → 分发到采集端或查看端处理
             消费掉 line_len 字节（见 §5.3）
```

这样无论 TCP 怎么分片都能正确工作。

### 5.3 首行消费必须只移出该行（修 D7）

**现状问题**：`handle_resource()` 和 `generate_http_response()` 都调用了
`memset(conn->inbuf, 0, CONNECT_BUF_LEN)`，把**整个 512KB 缓冲区**清零。

如果采集端把握手行和第一帧放在同一个 `send()` 里发出（TCP 完全可能合并），
这一帧就被丢掉了。HTTP 侧同理，会丢掉紧跟在请求头之后的数据。

**正确做法**：只把已消费的字节 `memmove` 出去，其余保留：

```
remain = inlen - line_len
if (remain > 0)
    memmove(inbuf, inbuf + line_len, remain);
inlen = remain;

/* 若 remain > 0 且当前是采集端阶段，这些字节正是待解析的帧数据，
   交给帧解析逻辑继续处理即可（不要丢） */
```

### 5.4 查看端标识：账号写在 URL 路径里

**不使用 HTTP Basic，不解析任何认证头。** 账号直接从请求行第一段取：

```
GET /alice HTTP/1.1\r\n
    ^^^^^^
    账号
```

**为什么不用 Basic**：既然不校验密码，Basic 认证就退化成形式主义 ——
仍要浏览器弹框、输入无人校验的密码、服务器解 Base64 再丢掉密码部分。
账号写在路径里则从"实现一个认证协议"退化为"切一段字符串"。

**代价**：账号名明文出现在 URL 和服务器访问日志里。
反正不校验密码本就没有安全性可言，这个代价可以接受。

### 5.5 路径规划（展开）

#### 5.5.1 现状：路径完全没被解析

浏览器打开 `http://127.0.0.1:8888/` 时，实际发出：

```
GET / HTTP/1.1\r\n
Host: 127.0.0.1:8888\r\n
User-Agent: Mozilla/5.0 ...\r\n
Accept: text/html,...\r\n
\r\n
```

但 [generate_http_response()](codes/reactor/src/http/http_handler.c#L40) **从未看过 `GET` 后面跟的是什么**：

```c
int generate_http_response(struct connect* conn) {
    int status_code = http_get_status_code(conn->inbuf);   // 恒返回 200
    ...
    conn->outlen = snprintf(conn->outbuf, CONNECT_BUF_LEN,
            "HTTP/1.1 200 OK\r\n"
            "Content-Type: multipart/x-mixed-replace; boundary=frame\r\n"
            ...
```

结果：`GET /`、`GET /alice`、`GET /favicon.ico`、`GET /随便什么`
**全部走进同一分支，全部回 200 + MJPEG 流**。

> 这就是 D3：`struct_http.path` 预留了 256 字节字段，却从未赋值。

#### 5.5.2 为什么加账号就必须改这里

**"看哪个账号的视频"这个信息，唯一来源就是请求行里的路径。**

```
GET /alice HTTP/1.1
     ^^^^^^
     账号在这里
```

现在的代码读完 `GET ` 就把后面全扔了，服务器无从知道你要看 alice 还是 bob，
`viewer_broadcast()` 自然也只有一个全局数组可发。

#### 5.5.3 改造后的完整流程

```
浏览器: GET /alice HTTP/1.1\r\nHost: ...\r\n\r\n
            │
            ▼
   recv_callback() 把字节收进 inbuf
            │
            ▼
   ┌──────────────────────────────────────────────┐
   │ PHASE_PRE_AUTH：在 inbuf 里找 "\r\n"          │
   │   未找到且 inlen <= 128 → return，等下一包     │
   │   未找到且 inlen > 128  → 非法，关闭连接       │
   │   找到 → 首行 = inbuf[0 .. \r\n 之前]          │
   └──────────────────────────────────────────────┘
            │
            ▼
   首行 = "GET /alice HTTP/1.1"
            │
            ▼
   ┌──────────────────────────────────────────────┐
   │ 切出 method 与 path                          │
   │   method = "GET"                             │
   │   path   = "/alice"  → conn->app.http.path   │
   └──────────────────────────────────────────────┘
            │
            ▼
   ┌──────────────────────────────────────────────┐
   │ 路径路由（新增）                              │
   ├──────────────────────────────────────────────┤
   │ method != "GET"      → 405                   │
   │ path == "/"          → 503 + 提示页           │
   │ path 含第二个 '/'    → 404（只支持一层）      │
   │ path == "/favicon.ico" → 404                 │
   │ account_name_valid() 失败 → 404              │
   │ account_verify() 失败 → 404                  │
   │ 全部通过             → 200 + MJPEG 流         │
   └──────────────────────────────────────────────┘
            │
            ▼
   通过 → viewer_register(账号下标, conn)
            │
            ▼
   消费掉首行（memmove，不是 memset！见 §5.3）
            │
            ▼
   send_cb = http_callback，之后每帧走转发
```

#### 5.5.4 各路径的响应报文

**① `GET /` —— 只给了根路径，没给账号**

```
HTTP/1.1 503 Service Unavailable\r\n
Content-Type: text/html; charset=utf-8\r\n
Content-Length: <n>\r\n
Connection: close\r\n
\r\n
<html><body><h3>请指定账号</h3>
<p>访问格式： <code>/&lt;账号&gt;</code>，例如 <code>/alice</code></p>
</body></html>
```

> **为什么不列出可用账号**：列出来等于任何人打开首页就知道所有通道名，
> 与本设计"账号即访问凭据"的定位冲突。默认**不列**。
>
> 若演示时希望少打字，把 `config.h` 里的 `ALLOW_INDEX_PAGE` 设为 1，
> 该页面会列出账号表并给出可点链接。**默认 0**。

**② `GET /alice` —— 正常看流**

```
HTTP/1.1 200 OK\r\n
Content-Type: multipart/x-mixed-replace; boundary=frame\r\n
Connection: keep-alive\r\n
Cache-Control: no-cache\r\n
\r\n
--frame\r\n
Content-Type: image/jpeg\r\n
Content-Length: 34512\r\n
\r\n
<JPEG 字节>
\r\n
--frame\r\n
...（持续）
```

这就是现在 `generate_http_response()` 已经在做的事，
只是**前面多了一步"确认 alice 这个账号存在"**。

**③ `GET /favicon.ico` —— 必须能正确回 404**

浏览器打开任何页面都会**自动**请求 `/favicon.ico`。现在这个请求会被当成
"要看视频流"，于是浏览器多开一条永不结束的 MJPEG 连接挂在那。
加路由后它会正确拿到 404 然后结束。

> 这是路径路由的一个**独立收益**，不只是为了账号。

#### 5.5.5 路径 → 响应对照表

| 请求行 | 条件 | 响应 | 连接后续 |
| --- | --- | --- | --- |
| `GET /` | — | `503` + 提示 HTML | 关闭 |
| `GET /alice` | 账号存在 | `200` + multipart | **保持，开始推流** |
| `GET /alice` | 账号不存在 / 名字非法 | `404` | 关闭 |
| `GET /alice/xxx` | 含第二层路径 | `404` | 关闭 |
| `GET /favicon.ico` | 保留字 | `404` | 关闭 |
| `POST /alice` | 非 GET | `405` | 关闭 |
| 首行 > 128 字节无 `\r\n` | — | 关闭（防慢速攻击） | 关闭 |

#### 5.5.6 一层路径的已知约束

选定"只支持一层"后，**账号名占用了整个 URL 命名空间**：

- 现在没有 `/status`、`/record`、`/login` 这类端点，无冲突
- 将来若要加，必须先把路由改成 `/stream/<account>` 前缀形式，
  否则一个叫 `status` 的账号会和 `/status` 端点撞车
- **缓解措施**：在 `§4.2` 的账号名保留字里预先加上 `favicon.ico`，
  并在文档 §9 记录这个约束，说明"扩展时需引入路径前缀"

#### 5.5.7 改造前后对照

| | 改造前 | 改造后 |
| --- | --- | --- |
| 路径 | 完全不解析 | 从首行切出，存进 `conn->app.http.path` |
| 账号来源 | 无 | 路径第一段 |
| 谁决定看哪路视频 | 没有这个能力（全局广播） | 路径账号 → 账号表 → 该账号的采集端 |
| `favicon.ico` | 挂一条僵尸 MJPEG 连接 | 正确 404 |
| 首行分片 | 不支持（D6） | 按完整行解析，天然支持 |
| 状态码 | 只有 200 | 200 / 404 / 405 / 503 |

## 六、并发模型与同步

### 6.1 数据竞争问题

`config.h` 里 `NUM_OF_REACTOR = NUM_OF_THREAD = 2`，即有 **2 个 sub reactor 线程**。
不同连接被 `get_next_reactor()` 轮流分配到不同线程。

于是账号表 `g_accounts` 是**被多个线程共享的可变全局状态**：

| 操作 | 执行线程 |
| --- | --- |
| 采集端注册 → 写 `g_accounts[i].cam_fd` | 采集端所在 reactor 线程 |
| 查看端访问 → 读 `g_accounts[i].cam_fd`，写 `viewers[]` | 查看端所在 reactor 线程 |
| 采集端断线 → 清 `cam_fd` | 采集端所在 reactor 线程 |
| 查看端断线 → 清 `viewers[]` | 查看端所在 reactor 线程 |

两条连接完全可能落在不同线程上，**无保护就是数据竞争**。
（若将来把 `NUM_OF_REACTOR` 调大，问题只会更明显。）

### 6.2 同步方案

采用**单把全局互斥锁**保护账号表：

```c
static pthread_mutex_t g_account_lock = PTHREAD_MUTEX_INITIALIZER;
```

### 6.3 锁粒度设计（关键）

**千万不要**把 `viewer_broadcast()` 整个放进锁里 —— 那是每帧都要走的路径，
会把并发的视频转发串行化，直接抵消多 reactor 的意义。

正确的划分：

```
┌─────────────────────────────────────────────────────────┐
│  临界区（持锁）                                           │
│    · account_verify(name)              → 查下标          │
│    · account_bind_camera(idx, fd)      → 绑定 + 反向索引  │
│    · account_unbind_camera(fd)         → 解绑            │
│    · account_add_viewer(idx, fd)       → 加订阅          │
│    · account_remove_viewer(fd)         → 去订阅          │
│    · account_snapshot_viewers(idx,out) → 拷贝 fd 列表     │
│    · account_touch_frame(idx, ts)      → 更新 last_frame_ms│
└─────────────────────────────────────────────────────────┘
                            │
                            ▼
┌─────────────────────────────────────────────────────────┐
│  非临界区（不持锁）                                       │
│    · 帧解析（找魔数 / 校验 / 校验和）                      │
│    · recorder_write_frame()   磁盘 I/O，绝不能持锁         │
│    · push_frame_to_viewer()   往 outbuf 拷数据             │
│    · set_epoll()              跨线程通知                  │
└─────────────────────────────────────────────────────────┘
```

`viewer_broadcast()` 的推荐写法：

```
1. 持锁 → 由 cam_fd 查出账号下标 → 把 viewers[] 拷贝到本地数组 → 放锁
2. 不持锁，遍历本地数组逐个 push_frame_to_viewer()
```

**代价**：快照期间新加入的查看端会漏掉当前这一帧（下一帧就能收到）。
这是可接受的 —— 视频流本来就不保证首帧必达。

**为什么可以用单锁**：绑定/上下线都是**低频操作**（每连接一次），
持锁时间以微秒计，不会成为瓶颈。真正的热路径（每帧转发）在锁外。

### 6.4 跨线程唤醒查看端（含 D8 修复）

查看端可能和采集端在不同 reactor 线程上，往查看端的 `outbuf` 写完数据后，
需要让**查看端自己的 epoll 实例**产生 `EPOLLOUT` 事件把它发出去。

**现有机制已支持**：

```c
/* src/epoll.c —— 直接调 epoll_ctl，没有额外的事件队列 */
void set_epoll(struct reactor* reactor, int EVENT, int OPERATION, int fd);
```

Linux 的 `epoll_ctl()` 对 epoll 实例是**线程安全**的，
所以 A 线程可以对 B 线程的 epfd 调用 `EPOLL_CTL_MOD`。

**但有两个前提**：

1. **只有 `epoll_ctl` 是线程安全的，`epoll_wait` 不是**。
   所以只能"改事件掩码"，不能由 A 线程替 B 线程取值。
   当前设计正是只做 `EPOLL_CTL_MOD`，符合要求。

2. **必须保证 epfd 已经创建** —— 这就是 **D8**：

```c
void* func_reactor(void* arg) {
    sub->epfd = epoll_create(1);   // ← epfd 在线程启动之后才创建
    ...
}
void init_sub_reactor(void) {
    for (...) pthread_create(...);  // 线程在这里启动
    sem_post(&sub_init);            // ← 但信号在这里就发了，早于 epfd 创建
}
```

`main()` 用 `sem_wait_timeout(&sub_init, 500)` 等的是 **500ms 超时**，
不是"epfd 建好了"。如果主线程在这之前 accept 到连接并 `set_epoll()`，
那次 `epoll_ctl` 会因 `epfd == 0` 失败，而且**返回值被忽略**。

**修复（两处，都很小）**：

- 把 `sem_post(&sub_init)` 移到 `epoll_create()` **之后**，
  让 `main()` 等到的信号真正代表"reactor 就绪"
- `set_epoll()` 检查 `epoll_ctl()` 的返回值，失败时打印 `fd` 与 `errno`

> 单机自测不容易碰到这个竞态，但账号体系会让跨线程通知变频繁，**建议顺手修掉**。

## 七、状态机与边界情况

### 7.1 统一连接状态机

当前用 `serve_type` 一个字段同时表达"角色"和"阶段"，加账号后不够用。
引入显式阶段字段：

```c
enum conn_phase {
    PHASE_PRE_AUTH,       /* 已 accept，等完整首行 */
    PHASE_CAM,            /* 采集端已注册，收自定义协议帧 */
    PHASE_VIEWER,         /* 查看端已登记，可能已开始推流 */
    PHASE_CLOSED
};
```

```
                    ┌────────────────┐
     accept ───────▶│ PHASE_PRE_AUTH │
                    └───────┬────────┘
                            │ 收到完整首行（含 \r\n）
              ┌─────────────┼─────────────┐
              │ "CAM ..."   │ "GET ..."   │ 其它
              ▼             ▼             ▼
        校验账号名      切出 method/path  回 400
              │             │            并关闭
      ┌───────┴───────┐     │
      │               │     │
   合法且空闲      非法/占用 │
      │               │     │
      ▼               ▼     ▼
 回 OK         回 ERR AUTH  路径路由
 PHASE_CAM     或 ERR BUSY  （见 §5.5.3）
 (绑定账号)     并关闭        │
                        ┌────┴────┐
                        │         │
                     通过       失败
                        │         │
                        ▼         ▼
                  PHASE_VIEWER  404/405/503
                  (加入 viewers) 并关闭
```

### 7.2 查看端先连、采集端后连（重要）

**场景**：查看端访问 `/alice` 成功，但该账号的采集端还没上线。

**方案对比**：

| 方案 | 做法 | 评价 |
| --- | --- | --- |
| A | 挂住请求不回响应，等采集端上线再回 200 + 流头 | 简单，但浏览器长时间无响应可能超时或一直转圈 |
| B | 直接回 503 让用户刷新 | 实现最简，但体验差、要手动刷新 |
| **C** | **立刻回 200 + MJPEG 流头，先推"等待设备"占位图；采集端上线后无缝切换成真实帧** | **推荐** |

方案 C 的要点：

- 服务器内置一张 `waiting.jpg`（编译进去或启动时读入内存），
  用与真实帧相同的 MJPEG 分段格式循环推送（`VIEWER_IDLE_FPS`，默认 1 fps 即可）；
- 采集端注册成功时，**不需要给查看端发任何"开始"信号** ——
  下一帧真实数据自然就把占位图顶掉了；
- 好处：**查看端的 code path 只有一条**（"往 outbuf 写 MJPEG 分段"），
  不需要为"等待中"单独维护状态和分支。

> 这也是 IP 摄像头和流媒体服务器的常见做法（先建立流，内容后到）。

**占位图从哪来**：建议在 `main()` 启动时从一个文件读入内存
（`config.h` 里配 `WAITING_IMG`，默认 `./waiting.jpg`）。
读不到就退化成方案 B（回 503），并在日志里告警。

### 7.3 同一账号第二个采集端（拒绝而非顶替）

**已确认选择"拒绝"**。理由：

- **顶替的语义更危险**：真实场景下可能是配置错误，或者现场有两台设备
  配成了同一个账号。静默顶替会让先来的设备莫名掉线，难以排查。
- **拒绝的行为可预期**：新连接收到 `ERR BUSY` 后被关闭，
  日志明确记录「账号 alice 已有采集端 fd=7，拒绝 fd=12」。

**断线重连的配合**：采集端掉线时 `close_callback` 会解绑账号，
所以正常重连不会撞上 BUSY。但如果**旧连接的 TCP 还没被内核回收**
（设备断电后立刻重启，或网络抖动），会出现短暂 BUSY。

**处理：僵死连接超时顶替**

```
account_bind_camera(idx, fd, now_ms):
    若 cam_fd == -1                          → 直接绑定
    若 cam_fd != -1 且 now - last_frame_ms > CAM_STALE_MS(10000)
                                             → 关闭旧连接，绑定新连接
    否则                                      → 返回 BUSY
```

`last_frame_ms` 在每帧广播前更新（`account_touch_frame`，持锁但极快）。

### 7.4 边界情况清单

| 场景 | 处理 |
| --- | --- |
| 账号不存在（采集端） | 回 `ERR AUTH` 后关闭 |
| 账号名非法（采集端） | 回 `ERR AUTH` 后关闭 |
| 账号已占用（采集端） | 回 `ERR BUSY` 后关闭 |
| 账号不存在（查看端） | 回 404（不区分"不存在"和"名字非法"，避免枚举） |
| 首行超过 128 字节仍无 `\r\n` | 判定非法，回 400 / 直接关闭（防慢速攻击占内存） |
| 请求方法不是 GET | 回 405 |
| 路径含第二层（`/alice/x`） | 回 404 |
| 请求 `/favicon.ico` | 回 404（保留字，见 §4.2） |
| 账号名含 `/` `?` `#` 空格 | 配置加载与握手阶段均拒绝 |
| 账号名含 `:` | 配置解析时拒绝（`:` 是分隔符） |
| 采集端掉线 | 解绑账号、清反向索引、**保留**查看端连接（继续推占位图） |
| 查看端掉线 | 从 `viewers[]` 摘除，不影响采集端与其它查看端 |
| 查看端数量超上限 | 回 503 并关闭（或允许但打日志，二选一） |
| 配置文件缺失 | 启动告警；所有采集端 `ERR AUTH`，所有查看端 404 |
| 配置文件语法错误 | 跳过该行并打印行号，不中断启动 |
| 配置里账号名重复 | 保留第一个，后续跳过并告警 |
| 占位图文件缺失 | 退化为"查看端先连时回 503" |

## 九、后续扩展点

按性价比排序：

1. **启用密码校验**：`struct account.password` 和配置文件的第二列都已预留，

## 十一、实现顺序建议

按"每步都能独立验证"的顺序推进：

| 步骤 | 内容 | 验证方式 |
| --- | --- | --- |
| 0 | **修 D8**（`sem_post` 时序 + `set_epoll` 检查返回值） | 启动打印，确认无 `epoll_ctl` 失败 |
| 1 | `struct connect` 加 `phase` / `account_idx`；重写首行解析为"按完整行" | 用 `nc` **分片**发送 `GET /alice HTTP/1.1\r\n`，确认正确识别 |
| 2 | 账号表 + 配置加载 + `account_name_valid()`（先不做路由） | 启动时打印加载到的账号数；故意写坏几行看是否跳过 |
| 3 | 采集端握手改造 + `OK`/`ERR` 回应 + 绑定 | `fake_cam` 分别用合法、不存在、已占用的账号各试一次 |
| 4 | 查看端路径路由 + 404/405/503 | 浏览器访问 `/`、`/alice`、`/favicon.ico`、`/alice/x` 逐个核对 |
| 5 | `viewer_broadcast()` 改为按账号转发 | 两个账号 + 两个 `fake_cam`，确认互不串流 |
| 6 | 占位图 + 采集端上线无缝切换 | 先开浏览器再开 `fake_cam`，确认自动出画面 |
| 7 | 僵死超时顶替 + 边界情况与日志完善 | 模拟断电重连；确认超时后新连接能接管 |

**第 1 步单独做**，因为它会改动现有的连接识别主流程，
是唯一一个"改错了整个服务器都不工作"的地方，值得先隔离验证。

## 附录 C：账号名合法性校验（三处共用）


**必须在三处调用，保持行为一致**：

| 调用点 | 时机 |
